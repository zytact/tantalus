# Following another Tantalus

A Tantalus can follow another one, the host, instead of reading its own sign-ins. Settings in local mode has a **Follow another Tantalus** row whose **Connect** button opens a form with **Address** and **Pairing code**. The address is one the host's Settings lists, and a bare `host:port` means `http://`. The code comes from **Pair a device** on the host (see `remote-access.md`).

Connecting first reads the host's unauthenticated `GET /api/version`, which answers `{"protocol": 2, "name": "<host machine name>", "id": "<host ID>"}`. The host ID is a random UUID the host saves once in `host-id.json` in its settings directory. A host on another protocol is refused with `Update Tantalus on <host>.` or `Update Tantalus on this device to connect to <host>.` A host from before pairing has no version and reads as one to update. The client then posts the code to `/api/pair` with `x-tantalus-action: pair-app` and its own machine name. A wrong code reads `That code is wrong or has expired.` and saves nothing. On success the host lists the client under its machine name, and the client saves `host-link.json` in its settings directory with the host name, the host ID, the routes as `[{"url": ..., "found": false}]` and the token. A file saved before routes holds a single `url` instead. It loads as one typed route with no ID, and the client takes the ID from that address on its next connect. The token is sealed by `safeStorage` as `{"sealed": ...}` where the keychain works, otherwise kept as `{"plain": ...}`.

While following, the client polls nothing and serves nothing. Its remote access listener stops, and its own provider and hub settings files are left alone. It follows the host's `/api/events` with `Authorization: Bearer`, and shows exactly the host's snapshot: direct providers, hub accounts, pace and window starts. The allowance status reads `Refreshed ... on <host>`. Refresh, in the window or the tray, posts to the host's `/api/refresh`. Hub sections have no **Hub** management link, since the hub belongs to the host. Settings shows **Following <host>** with a status dot (green connected, amber connecting, red otherwise), a state line (`Connected`, `Connecting`, `Unreachable since <time>`, or the removed or update text) and **Disconnect**, then the Routes group (see below), then the host's update row (see below), then only tray usage, Open at login and the version row. Providers, hubs, pace, window start, Follow another Tantalus, remote access and paired devices are hidden. Host toasts do not reach the client.

## Routes

After each connect, and every 30 seconds while following, the client reads the host's paired-only `GET /api/routes`, which answers `{"urls": [...], "complete": true}`: the Tailscale URL first, then each Local network URL, the same lists the host's Remote access rows show. `complete` is false while the host's Tailscale switch is on but `tailscale status` did not give its address. The client saves the URLs as found routes beside the ones typed on it. A found route a complete report leaves out is dropped unless it is in use. An incomplete report only adds routes, and a failed `/api/routes` changes nothing. A host from before routes reports no ID, so the client keeps its one address.

A route whose host is a `.ts.net` name or a `100.64.0.0/10` address is Tailscale, and any other is Local network. Tailscale routes come first, since the Local network route is plain HTTP, and within a kind HTTPS comes first, so the `ts.net` route ranks above the host's `100.x` address. Each attempt asks every route's `/api/version` at once and streams from the most preferred one that answers with the saved ID. A route answering with another ID never gets the token. While streaming from a route with a preferred one above it, the client asks the preferred ones every 30 seconds, right after reading the routes again, and moves to the first that answers, without showing a banner. A route the host switches back on is found this way without the stream dropping.

The Routes group in Settings lists every route in preference order. Each row has a Tailscale or Wi-Fi icon, the route name, `· found automatically` for a found route, the URL, and an `In use` pill on the route delivering usage. A last **Add route** row opens an **Address** field with **Add** and **Cancel**. The client reads the address's `/api/version` before saving it as a typed route. It refuses `<url> is another Tantalus, not <host>.` for another ID, `<url> is already a route.` for a listed one, and `Update Tantalus on <host> to add routes.` for a host with no ID. When every route is one kind and at least one was found, a note under the group says to switch the other route on in the host's Remote access settings. Routes cannot be removed or reordered.

## The host's update

Below Routes, Settings has a **Tantalus on <host>** row with a **Check <host> for updates** button, named after the host because the version row below keeps its own **Check for updates** for this machine. It sends the host the same `POST /api/check-update` the browser page does (see `remote-access.md`), with the bearer token, over the route in use. `Tantalus on <host> is up to date.` shows for no update, and a failure shows the host's own words as an alert. The client reads `hostUpdate` and `hostInstallProgress` from the host's stream, so the host's banner `Version <x> is available on <host>.` shows below the row and below the Allowance header, also when the host's background check found the release. **What's new** reads the host's `/api/release-notes` and is headed `Up to v<x> on <host>`. **Install update** posts the acknowledged notice ids to `/api/update`. The host restarts instead of answering, so a request it drops after receiving it is no failure, while one that reaches no route reads `Could not reach <host>.` A host from before this answers 404 or 405, which reads `Tantalus on <host> is too old to update from here. Update it on <host> first.` A request the host or a proxy drops reads `<host> stopped answering.` While the host restarts the client shows the unreachable banner and reconnects by itself (see Outages). The row and banner are hidden once the host removes the device, and the host's update is forgotten on disconnect.

## Outages

The host pings every open stream every 15 seconds. After 45 seconds of silence, or when the stream drops and the next attempt finds no route that answers, the client shows a banner `<host> is unreachable. Since <time>. Showing usage from <time>.` and keeps the last snapshot. The tray tooltip adds the same problem line and a tray usage number turns gray. It retries after 1 second, doubling to 30, without limit, and the banner disappears once a snapshot arrives. A route that hangs holds each attempt for up to 10 seconds. A 401 means the host removed the device. The banner reads `<host> removed this device. Pair again in Settings.` with the same Since and Showing times, retries stop, and Settings keeps **Following <host>** and **Disconnect** with the connect form below, its address filled in with the first route. **Disconnect** deletes `host-link.json`, starts local polling, restarts the saved remote access routes and shows this machine's usage again. A restart while following resumes following.

## Preview proof

This needs two previews, so it needs two checkouts. Each checkout has its own run directory, display, settings and DevTools port, and only the host listens on 4748. Make a second worktree of the same branch for the client, install it, and run `build-preview.sh` there too.

1. In the host checkout, `launch.sh --mock ready`, add the fixture hub per `proxy-hubs.md` if hub accounts should be proven, switch Local network on and click **Pair a device**. Read the code from a snapshot.
2. In the client checkout, `launch.sh --mock idle` so its own readings differ from the host's. Open Settings, click **Connect**, fill `textbox "Address"` with `127.0.0.1:4748` and `textbox "Pairing code"` with the code, then click `button "Connect"`. The client's Settings shows **Following <host>**, and the allowance page shows the host's `ready` figures and `on <host>` in the status. The host lists the client under its machine name as `Connected`.
3. Confirm the client's fixture log gets no new requests while following, and record whether `host-link.json` holds `sealed` or `plain`. It depends on whether the desktop session's keyring is reachable from the Xvfb launch, and either is correct. Never print the token.
4. Click Refresh on the client and confirm the host's fixture log records the reads.
5. Run `cleanup.sh` in the host checkout, or switch the host's Local network off. Within 45 seconds the client shows the unreachable banner with both times, and its allowance figures stay. Relaunch the host or switch Local network on again, and the banner clears.
6. Remove the client in the host's Settings. The client shows the removed banner, its Settings shows the connect form with the address filled in, and the client stops requesting. The **Tantalus on <host>** row and its check button are gone while removed, and come back once it pairs again. Pair again with a fresh code.
7. Run `launch.sh --restart` in the client checkout and confirm it resumes following.
8. Routes, which needs Tailscale signed in with Serve allowed (see `remote-access.md`). Switch both Local network and Tailscale on in the host and pair the client over the host's LAN address, such as `http://192.168.1.5:4748`. The Routes group lists that address as typed, and the host's `ts.net` URL and its `100.x` address as `found automatically`. Within 30 seconds `In use` moves to the `ts.net` route. Switch Tailscale off on the host. A stream already open through Tailscale Serve survives `serve off`, so run `launch.sh --restart` in the client checkout to make it connect again. It comes back on the next route that answers, the `100.x` address, with no banner. Switch Tailscale on again and `In use` returns to the `ts.net` route within 30 seconds. Switch Local network off on the host, leaving Tailscale on. That closes every open connection, and the client reconnects on the `ts.net` route while the LAN routes stop answering. Switch Local network on again.
9. Add `127.0.0.1:4748` with **Add route** and confirm it is listed as typed. Start a stand-in that answers `/api/version` with another ID, such as `python3 -c 'import http.server as h; h.HTTPServer(("127.0.0.1", 47499), type("H", (h.BaseHTTPRequestHandler,), {"do_GET": lambda s: (s.send_response(200), s.end_headers(), s.wfile.write(b"{\"protocol\":2,\"name\":\"x\",\"id\":\"other\"}"))})).serve_forever()'`, add `127.0.0.1:47499` and confirm the refusal, then stop it.
10. Rewrite the client's `host-link.json` under `mock-home/config/dev.arnab.tantalus.preview/` in its run directory to the old form `{"url": <first route>, "host": ..., "token": ...}` with a script that never prints the token, then run `launch.sh --restart` in the client checkout. A steady link does not rewrite the file, so the old form is what the restart loads. Confirm it follows again, and that `host-link.json` gains the ID and the found routes.
11. The host's update. On the client, click `button "Check <host> for updates"`. A preview host refuses, so the alert under the row reads `Dev and preview builds do not check for updates.`, and the client's own `button "Check for updates"` shows the same text under the version row. Capture both schemes. Then run `launch.sh --restart` in the host checkout and confirm the client goes through the unreachable banner back to `Connected` without being touched. The found-update flow needs a release host (see `updates.md`).
12. Click **Disconnect** on the client. Its own `idle` readings return, its fixture log shows reads again, and `host-link.json` is gone.

Capture both schemes for the connect form, the following Settings with its Routes group, the Add route form, the unreachable banner and the removed banner. Run `cleanup.sh` in both checkouts, then remove the client worktree.
