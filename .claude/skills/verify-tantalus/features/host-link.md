# Following another Tantalus

A Tantalus can follow another one, the host, instead of reading its own sign-ins. Settings in local mode has a **Follow another Tantalus** row whose **Connect** button opens a form with **Address** and **Pairing code**. The address is one the host's Settings lists, and a bare `host:port` means `http://`. The code comes from **Pair a device** on the host (see `remote-access.md`).

Connecting first reads the host's unauthenticated `GET /api/version`, which answers `{"protocol": 1, "name": "<host machine name>"}`. A host on another protocol is refused with `Update Tantalus on <host>.` or `Update Tantalus on this device to connect to <host>.` A host from before pairing has no version and reads as one to update. The client then posts the code to `/api/pair` with `x-tantalus-action: pair-app` and its own machine name. A wrong code reads `That code is wrong or has expired.` and saves nothing. On success the host lists the client under its machine name, and the client saves `host-link.json` in its settings directory with the URL, the host name and the token. The token is sealed by `safeStorage` as `{"sealed": ...}` where the keychain works, otherwise kept as `{"plain": ...}`.

While following, the client polls nothing and serves nothing. Its remote access listener stops, and its own provider and hub settings files are left alone. It follows the host's `/api/events` with `Authorization: Bearer`, and shows exactly the host's snapshot: direct providers, hub accounts, pace and window starts. The allowance status reads `Refreshed ... on <host>`. Refresh, in the window or the tray, posts to the host's `/api/refresh`. Settings shows **Following <host>** with the URL and **Disconnect**, then only tray usage, Open at login and the version row. Providers, hubs, pace, window start, Follow another Tantalus, remote access and paired devices are hidden. Host toasts do not reach the client.

The host pings every open stream every 15 seconds. After 45 seconds of silence, or when the stream drops, the client shows a banner `<host> is unreachable. Since <time>. Showing usage from <time>.` and keeps the last snapshot. The tray tooltip adds the same problem line and a tray usage number turns gray. It retries after 1 second, doubling to 30, without limit, and the banner disappears once a snapshot arrives. A 401 means the host removed the device. The banner reads `<host> removed this device. Pair again in Settings.`, retries stop, and Settings shows the connect form again with the address filled in. **Disconnect** deletes `host-link.json`, starts local polling, restarts the saved remote access routes and shows this machine's usage again. A restart while following resumes following.

## Preview proof

This needs two previews, so it needs two checkouts. Each checkout has its own run directory, display, settings and DevTools port, and only the host listens on 4748. Make a second worktree of the same branch for the client, install it, and run `build-preview.sh` there too.

1. In the host checkout, `launch.sh --mock ready`, add the fixture hub per `proxy-hubs.md` if hub accounts should be proven, switch Local network on and click **Pair a device**. Read the code from a snapshot.
2. In the client checkout, `launch.sh --mock idle` so its own readings differ from the host's. Open Settings, click **Connect**, fill `textbox "Address"` with `127.0.0.1:4748` and `textbox "Pairing code"` with the code, then click `button "Connect"`. The client's Settings shows **Following <host>**, and the allowance page shows the host's `ready` figures and `on <host>` in the status. The host lists the client under its machine name as `Connected`.
3. Confirm the client's fixture log gets no new requests while following, and that `host-link.json` holds no raw token where `safeStorage` works. Under Xvfb without a keyring, expect `plain`.
4. Click Refresh on the client and confirm the host's fixture log records the reads.
5. Run `cleanup.sh` in the host checkout, or switch the host's Local network off. Within 45 seconds the client shows the unreachable banner with both times, and its allowance figures stay. Relaunch the host or switch Local network on again, and the banner clears.
6. Remove the client in the host's Settings. The client shows the removed banner, its Settings shows the connect form with the address filled in, and the client stops requesting. Pair again with a fresh code.
7. Run `launch.sh --restart` in the client checkout and confirm it resumes following.
8. Click **Disconnect** on the client. Its own `idle` readings return, its fixture log shows reads again, and `host-link.json` is gone.

Capture both schemes for the connect form, the following Settings, the unreachable banner and the removed banner. Run `cleanup.sh` in both checkouts, then remove the client worktree.
