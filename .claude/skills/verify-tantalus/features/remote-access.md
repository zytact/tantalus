# Remote access

Settings has two switches below Open at login, then the paired devices list. Both start off and save to `remote-access.json` in the settings directory. Nothing listens while both are off.

**Local network** makes the main process listen on `0.0.0.0` at the identity's web port, 4748 for the preview. The row lists `http://<address>:4748` for every non-internal IPv4 address, which includes the Tailscale address when Tailscale is up. **Tailscale** alone listens on `127.0.0.1` at the same port and runs `tailscale serve --bg --https=8444 http://127.0.0.1:4748`; with both switches on, the listener remains on `0.0.0.0`. The row shows `https://<machine>.<tailnet>.ts.net:8444`, read from `tailscale status --json`. Switching Tailscale off runs `tailscale serve --https=8444 off`. Each listed URL has a QR button that shows a scannable code for that URL below it. Tailscale keeps the route in its own config, so it survives a quit, and launch attempts `serve` again when the switch is saved on. Confirm the HTTPS URL after restart, since a saved switch alone does not prove Serve succeeded.

A change saves first, then listens, then runs Tailscale. If any step fails, the file and listener go back to how they were, the switch stays put, and an alert names the cause, such as `Port 4748 is already in use.` or `Tailscale is not signed in.` If the port is taken at launch, the saved switches stay on and Settings shows `Remote access is not being served. Port 4748 is already in use.` until the next successful change.

Only paired devices read usage. The built page's files are public, but `/api/events`, `/api/current/*`, `/api/routes`, `/api/release-notes`, `/api/refresh`, `/api/check-update` and `/api/update` answer 401 without a paired device's cookie or bearer token, and an unpaired browser shows a **Pair this device** form instead of the allowance view. Below the two route rows, **Paired devices** has a **Pair a device** button. It shows a 6-character code with a countdown from 5:00 and swaps the button for **Cancel**. The code lives only in memory. It pairs one device, expires after 5 minutes, and is withdrawn with a toast after 5 wrong attempts. `POST /api/pair` with `x-tantalus-action: pair` and `{"code": "..."}` answers 204 with an HttpOnly, SameSite=Strict cookie named `tantalus-4748` for the preview, or 403 `That code is wrong or has expired.` The device is named after its user agent, such as `Chrome on Linux`. Each paired device gets a row reading `Connected` while it follows usage, otherwise `Last seen ...` or `Not seen yet`, with **Rename** and **Remove**. `paired-devices.json` in the settings directory holds each device's id, name, times and a SHA-256 hash of its token, never the token. Remove ends the device's open stream at once, and the browser falls back to the pairing form. Pairings survive switching the routes off and on.

The page is the allowance view without Settings or the pace notice. It includes enabled direct providers and every enabled hub's Codex and Claude accounts; Opencode hubs are unsupported. It follows `/api/events` and then reads `/api/current/usageSnapshot`, so a publish during load is not lost. It also reads `/api/current/serverEpoch` for countdowns. The event stream sends three events on connect, `usageSnapshot`, `hostUpdate` and `hostInstallProgress`, and one more whenever any of them changes. Refresh posts to `/api/refresh` with `x-tantalus-action: refresh`; a POST without that header returns 405. Other resources only serve GET. A Host header that is not an IP address, a single-label or `.local` name, or a `ts.net` name gets a 403, and a path outside the built page gets a 404.

## The host's update

Above the footer the page has a **Tantalus on the host** row with a **Check the host for updates** button. It posts to `/api/check-update` with `x-tantalus-action: check-update`, which runs the host's own manual check and answers the update as JSON, or `null`. The row then reads `Tantalus on the host is up to date.`, or the page scrolls to the top, where the host's update banner shows below the header: `Version <x> is available on the host.` with **What's new** and **Install update**. The banner also appears on its own when the host's background check finds a release, since the stream carries `hostUpdate`. What's new reads `GET /api/release-notes`. Install update posts to `/api/update` with `x-tantalus-action: update` and `{"acknowledgedNoticeIds": [...]}`, nothing else, so the host installs only the release it already found. Notices show with their checkbox, and the install progress strip follows `hostInstallProgress`. A release that needs a fresh install shows a line saying so, with no button. See `updates.md` for the flow itself.

A failure the host explains answers 409 with the reason as text, which the page shows as an alert: `Dev and preview builds do not check for updates.`, `No update is ready to install.`, `Read and acknowledge the update notice before installing.` A body without a string list of `acknowledgedNoticeIds` answers 400. A host that installs restarts instead of answering, so the page takes a dropped install request as no failure.

The page follows the host through a restart. The browser retries a dropped stream itself. When the stream opens again the page fetches `/` and reloads only if the served page changed, which is how it picks up the build the host updated into. A proxy such as Tailscale Serve answers 502 while the host is away, which closes the stream for good, so the page then asks `/api/current/serverEpoch` every 3 seconds and reloads once the host answers. A removed device gets 401 there and reloads into the pairing form.

## Preview proof

Launch with `--mock ready`, enable Opencode, and add the fixture hub per `proxy-hubs.md`. Open Settings and switch Local network on. Confirm the addresses, `{"localNetwork":true,"tailscale":false}` in `mock-home/config/dev.arnab.tantalus.preview/remote-access.json`, and a listener on `0.0.0.0:4748`. Show each address's QR code, screenshot it, and decode the image, which must return that address exactly. Load one listed address with `drive.ts --web` and confirm the pairing form. Click **Pair a device**, read the code from a snapshot of the window, then `drive.ts --web <url> submit textbox "Pairing code" <code>`. Each `--web` command loads a fresh page, so typing and submitting must happen in that one command. The `--web` profile keeps the cookie until cleanup. Confirm the device row reads `Connected` while a `--web` command holds the page open, the code row is gone, and `paired-devices.json` holds no token. Confirm Opencode and both hub accounts render with Refresh but no Settings or notices. Adding the fixture hub switches direct Codex and Claude off. Before adding it, confirm all three direct providers render. Both states show remaining headlines and Used facts, matching the preview window. For curl, pair a second device with a fresh code: `curl -si -X POST -H 'x-tantalus-action: pair' -d '{"code":"<code>"}' http://127.0.0.1:4748/api/pair` prints the `set-cookie` line, and later requests pass it as `-H 'cookie: tantalus-4748=<token>'`. Keep the token out of evidence. Without the cookie, `/api/current/usageSnapshot` returns 401. After setup refreshes finish, start a bounded SSE observer with `curl -sN --max-time 30 -H 'cookie: ...' http://127.0.0.1:4748/api/events`, complete two sequential remote refreshes, then stop the observer. Expect the initial event plus two refresh publications; background work can add events. Remove the curl device while the observer runs. The stream ends at once and the next request returns 401. Try five wrong codes against a fresh code and confirm the toast and that the right code then fails. For the host's update, run `drive.ts --web <url> click button "Check the host for updates" then wait 1 then snapshot`. Preview must show the alert `Dev and preview builds do not check for updates.` under the row. With the curl device, a bounded `/api/events` read starts with `event: usageSnapshot`, `event: hostUpdate` and `event: hostInstallProgress`. `POST /api/check-update` with its action header answers 409 with that same text, without the header 405, and without the cookie 401. `POST /api/update` with `x-tantalus-action: update` and `{"acknowledgedNoticeIds":[]}` answers 409 `No update is ready to install.`, and with `{"url":"https://example.com/x.rpm"}` 400. `GET /api/release-notes` answers 409 `No update is ready.` The banner, notes, notices and progress need a release host with a newer signed release (see `updates.md`). To prove the page survives a host restart, hold it open with `drive.ts --web <url> wait 25 then snapshot`, run `launch.sh --restart` meanwhile, switch the scenario with `mock-scenario.sh blocked` and click Refresh in the preview window. The snapshot must show the new scenario's figures. Do it once over a Local network address, where the browser reconnects by itself, and once over the `ts.net` URL, where `curl` on `/api/events` answers 502 while the preview is down. Probe with curl: `-H 'Host: evil.example'` returns 403, `--path-as-is /../package.json` returns 404, and POST to a page resource or Refresh without the action header returns 405.

For Tailscale, save `tailscale serve status` first and confirm nothing is on 8444. Switch Tailscale on, confirm the `ts.net` URL and the route to `127.0.0.1:4748`, and load that URL with `drive.ts --web`. Switch both off and diff `tailscale serve status` against the saved copy. This needs Tailscale installed, signed in, with Serve and HTTPS allowed on the tailnet, and on Linux an operator set with `sudo tailscale set --operator=$USER`. Without those, record the alert the switch shows instead.

To prove rollback, hold the port with a Python socket bound to `0.0.0.0:4748`, then switch Local network on. The switch stays off, the alert names the port, and the file is unchanged. To prove persistence and the launch message, switch both routes on and run `launch.sh --restart`. Both stay on, the listener returns, and the route is still there. Then stop the preview's recorded pid, bind the port again, run `launch.sh --restart`, and open Settings to read the launch alert. Free the port, and switch any route to clear it. Leaving Tailscale on is safe, since `cleanup.sh` removes the preview's route.
